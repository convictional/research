## 1. Context and goals

GEO Analyzer is an internal Convictional tool that measures how Convictional
shows up in answers from the most common generative AI products ("Generative
Engine Optimization"). It lives in the `convictional/decide` monorepo under
`experiments/geo-analyzer/` as a standalone Python subproject — independent of the
main product in `app/` and the R&D efforts in `experiments/`.

It runs a hand-authored catalog of prompts against multiple LLM providers in
both grounded (web-search enabled) and ungrounded (trained priors only)
modes, scores each response across a fixed set of metrics, and tracks those
metrics over time against explicit numeric goals.

It exists because:

1. Convictional is actively repositioning away from its legacy identity as a
   dropship software provider and toward a new category we are creating —
   "Organizational Health." We need quantitative evidence of how successful
   that repositioning is in the generative engines our prospects actually use.
2. SEO practices are giving way to GEO as a primary discovery channel. We need
   a dashboard that tracks our GEO the way marketing teams track SEO rankings.
3. We want to set goals for specific metrics (e.g., share of voice at a given
   prompt tier by a given date) and measure progress against them.

### 1.1 Measurement subjects

Every run scores against three subjects:

| ID                              | Kind       | Direction   | Notes                                                                             |
| ------------------------------- | ---------- | ----------- | --------------------------------------------------------------------------------- |
| `convictional_brand`            | Brand      | Grow        | Current Convictional positioning (Organizational Health platform).                |
| `organizational_health_category`| Category   | Grow        | Category creation signal — category awareness and definitional ownership.         |
| `convictional_legacy_dropship`  | Anti-brand | Shrink      | Residual association with the former dropship product. Want this to trend toward zero. |

### 1.2 Metrics

Top-line (primary scoreboard):

- **A. Mention presence** — binary, per response
- **B. Ordinal rank** — when the response contains an enumerated list, where does the subject appear?
- **C. Share of voice** — `mentions(subject) / (mentions(subject) + mentions(competitors))`
- **G. Brand-legacy conflation** (dropship confusion) — fires when `convictional_brand` and dropship terms co-occur in the same response. Headline metric for "is the repositioning working?" — this is **the** number we want to watch trend down.

Deferred to v2 (require ensemble judging, see §14):

- **D. Description accuracy** — `accurate | outdated | incorrect`
- **E. Sentiment** — `positive | neutral | negative`
- **F. Cited URLs** — captured in grounded mode; flagged when Convictional-owned domains appear (F is deterministic — could be in v1; deferred only because nothing else in v1 uses citation data yet)

### 1.3 Success criteria for v1

The tool is successful if, after 8 weeks of runs, the Convictional team can:

1. Open the latest `summary.md` (in `experiments/geo-analyzer/data/runs/<run-id>/`, generated by `geo-analyzer report`) and see the top-line scoreboard, funnel shape, and goal traffic-lights on one page.
2. Point at a specific metric movement and correlate it to a content or positioning change.
3. Set a new goal by editing `goals.yaml`, commit it, and see progress in the next run.

## 2. Non-goals (explicit out-of-scope for v1)

Aggressive scope discipline — v1 ships a useful harness first and iterates with evidence. Several features that landed in early drafts were pushed to v2 after team review.

**Deferred to v2** (design thinking captured in §14):

- **Ensemble judge pipeline** for subjective metrics (sentiment, description accuracy, brand-legacy association as an LLM-judged signal). v1 uses deterministic extraction only — including the dropship-conflation metric (G) which is a deterministic co-occurrence check and doesn't need a judge.
- **MCP server wrapper.** The CLI is rich enough for agent use; agents can call `geo-analyzer probe` directly. Dropping the MCP layer removes a whole file plus testing surface.
- **Scheduled automation (GitHub Actions cron).** v1 is a CLI run manually, or scheduled locally via `launchd` per-user. GH Actions cron is revisited once the harness proves valuable.
- **Slack alerts.** Exit code `3` still exists for future CI consumers; we just don't plumb it to Slack.
- **Perplexity, xAI, Mistral providers.** v1 targets the three providers most users actually encounter (OpenAI, Anthropic, Google) at their flagship models. Perplexity is inherently grounded (no clean ungrounded baseline); Mistral has no web-search API; xAI's search is beta.
- **`judge review` interactive TUI.** Becomes moot with judges deferred. When judges return in v2, start with a print-table + patch-file workflow and only build a TUI if volume justifies it.

**Also out of scope permanently (for v1 and likely beyond):**

- Browser automation against consumer UIs (ChatGPT.com, Gemini app, Claude.ai). Grounded API modes cover most of the signal.
- Persona-dimensioned prompts.
- Web UI / dashboard. The local `summary.md` is the dashboard.
- Competitor benchmarking beyond the share-of-voice math.
- Integration with `app/` or `experiments/`. The tool is isolated.

### 3.2 Prompt tiers

Prompts are organized into four specificity tiers:

| Tier | Name            | Example                                                        |
| ---- | --------------- | -------------------------------------------------------------- |
| L1   | Broadest        | "What's wrong with how modern companies are run?"             |
| L2   | Category-adjacent | "What tools help with employee engagement and culture?"     |
| L3   | Category-named  | "What is organizational health software?"                      |
| L4   | Brand-named     | "What is Convictional?"                                        |

The funnel shape — how score rises across tiers for each subject — is itself
a tracked metric. A healthy `convictional_brand` curve climbs steeply from L3
to L4. A healthy `organizational_health_category` curve shows rising L2 and
L3 scores over time.

## 4. Data model

Five core entities, all identified by stable hand-assigned string IDs so
catalog edits don't break historical comparability.

### 4.1 Subject

```yaml
id: convictional_brand
kind: brand              # 'brand' | 'category' | 'anti_brand'
aliases: [convictional, Convictional, convictional.com]
definition: >
  Convictional is a platform for organizational health, helping leaders
  improve how their companies are run through structured feedback,
  decision tracking, and alignment tools.
competitors:
  - lattice
  - culture_amp
  - 15five
  - workday
owned_domains: [convictional.com]   # used for cited-URL tagging
```

Fields:

- `kind` is the canonical anti-signal discriminator. Anti-signal logic triggers when `kind == "anti_brand"`; no separate `is_anti_signal` field (derived to avoid desync).
- `owned_domains` is captured in the per-task `citations` field for grounded responses but isn't scored in v1.
- No `detection_mode` field — co-occurrence detection for anti-brand subjects is standard; if a more elaborate detection model is needed later, it lands with the v2 judge pipeline.

### 4.2 Prompt

```yaml
id: prompt.category.l3.what-is-org-health
tier: L3
text: "What is organizational health software?"
targets: [convictional_brand, organizational_health_category]
version: 1
authored_at: 2026-04-23
```

Prompt IDs are permanent. Wording edits bump `version` but keep the ID so
historical scores stay comparable. Removing a prompt requires explicit migration.

### 4.3 Model

```yaml
id: openai:gpt-5.1:grounded
provider: openai
model_name: gpt-5.1
mode: grounded
active: true
config:
  tools: [{type: web_search}]
sampling:
  n: 3
  temperature: null   # null → use the provider's default temperature (§5.3)
  seed: 42            # passed where supported
```

Cross-generation tracking via a `cohort` field is deferred to v2 (§14).
v1 tests only the current cohort, so a per-model cohort label adds no
information.

Judge policy (which models act as judges, etc.) is also v2 — see §14.

### 4.4 Run

A single `geo-analyzer run` invocation. Identified by a `run_id`
(e.g., `2026-04-23`) plus trigger source (`manual`, `weekly-cron`, `monthly-cron`).

### 4.5 Task

A single `(run_id, prompt_id, model_id, sample_n)` tuple. Keyed uniquely —
re-running `geo-analyzer run` for the same day resumes missing tasks.

`sample_n` defaults to `0` for both grounded and ungrounded default runs
(see §5.3). It only takes non-zero values when the opt-in sensitivity mode
(§5.7) is explicitly enabled.

### 4.6 Score

Per `(run, subject, metric)` tuple (and `task` when not aggregated across grounded N=3 samples). Records:

- `value` — metric-specific (bool, int rank, float SoV)
- `scoring_method` — `deterministic` (only method in v1; v2 adds `judge_ensemble`, see §14)
- `sample_aggregation` — `single` | `majority_vote` | `median` | `mean`, describing how per-sample scores in grounded N=3 mode rolled up (§5.3)

## 5. Test execution model

### 5.1 Matrix

A full run expands to:

```
3 providers × 5 flagship models × 2 modes:
  Ungrounded: prompts (~30) × models (5) × 1 sample = ~150 calls
  Grounded:   prompts (~30) × models (5) × 3 samples = ~450 calls

No judge calls in v1 (deferred to v2 — see §14).
No historical-cohort runs in v1 (deferred to v2 — see §14).

---------------------------------------------------------------------------
≈ 600 API calls per run
```

Notes:

- **Grounded mode runs N=3 at each provider's default temperature** (typically 1 or 0.7) to simulate what a real user with web-search-enabled chat sees; the three samples are aggregated into both a binary majority-vote and a frequency rate per prompt×model (§5.3).
- **Ungrounded mode runs N=1 at temperature=0** to produce a clean training-priors baseline.
- `sample_n` is the sample index (0, 1, 2 for grounded N=3 tasks; always 0 for ungrounded).

### 5.2 Concurrency

- All provider calls run on `asyncio`.
- Per-provider `asyncio.Semaphore` caps concurrency per provider (e.g., OpenAI=8, Anthropic=5, Perplexity=2). Configured in `models.yaml` per provider.
- Retries with exponential backoff on 429s, 5xx, and timeouts. After `max_retries` (default 3), the task is recorded as `failed` with the error; the run continues and the report flags the gap.

### 5.3 Determinism and sampling

**Hybrid strategy:** the two modes serve different measurement purposes and use different sampling configurations.

| Mode       | Temperature                    | Samples (N) | What we're measuring                                                                     |
| ---------- | ------------------------------ | ----------- | ---------------------------------------------------------------------------------------- |
| Ungrounded | `0`                            | 1           | Training-priors baseline. Clean, deterministic; serves as the comparison anchor for v2's cross-generation curve.  |
| Grounded   | Provider default (~1 or ~0.7)  | 3, averaged | What a real user with web-search-enabled chat actually sees. Captures generation variance, which is where grounded-mode signal lives. |

**Why the asymmetry — three independent sources of variance:**

1. **Generation variance** — model's sampling randomness given the same prompt + context. Controlled by `temperature`. In **ungrounded** mode we want it pinned (the priors baseline must be stable); in **grounded** mode we want to sample at the real-user default because the reported experience *is* the real-user experience.
2. **Retrieval variance** (grounded only) — different search results at different times. Not controlled by `temperature` or `seed`. Captured by the **cadence itself** (week-over-week deltas), not within-run sampling.
3. **Provider non-determinism** — some providers don't guarantee seed determinism even at temp=0 (Anthropic is explicit about this). In ungrounded mode we accept the residual noise as small relative to our metric granularity.

**Grounded N=3 aggregation rules:**

Each binary metric emits **two score rows** per (run, prompt, model, subject) tuple — one binary, one rate:

| Metric                          | Aggregation           | Type            | Captures                                          |
| ------------------------------- | --------------------- | --------------- | ------------------------------------------------- |
| `mention_presence`              | majority vote (≥2/3)  | bool            | Did this prompt typically surface Convictional?   |
| `mention_presence_rate`         | mean (count true / N) | float [0,1]     | In what fraction of interactions did it surface?  |
| `brand_legacy_conflation`       | majority vote (≥2/3)  | bool            | Did this prompt typically conflate brand+legacy?  |
| `brand_legacy_conflation_rate`  | mean (count true / N) | float [0,1]     | In what fraction of interactions did it conflate? |
| `ordinal_rank`                  | median                | int or null     | Typical position in enumerated lists.             |
| `share_of_voice`                | mean                  | float           | Average SoV across samples.                       |

Why both: with N=3 samples per (prompt, model), Convictional might be conflated as dropship in 0, 1, 2, or 3 of the samples. Reporting `_rate` alongside the binary majority-vote tells two different stories:

- **Prompt-level (binary):** "for these prompts, the model's *typical* answer conflates the brand" (the majority case)
- **Interaction-level (rate):** "across these prompts, X% of all model interactions conflate the brand" (the user-experience case)

Cross-prompt aggregation in reports uses both — see §9.1.

**Per-sample values are preserved** in `tasks.jsonl` and `tasks.csv` keyed on `sample_n`, so any slice (specific prompt, specific provider, single sample) is a pandas filter away over the local run directory.

**Ungrounded mode (N=1):** rate metrics aren't emitted — they'd just equal 0.0 or 1.0 and add noise to schemas. Only the binary score is recorded.

**Seed handling:** where providers support it, we still pass a seed in grounded mode so re-runs against the same search index produce reproducible samples, which helps debug reported anomalies. Temperature stays at the default regardless.

**Sensitivity mode (§5.7) is still available** for investigating specific prompts at higher sample counts — but normal runs use the fixed N=3 grounded / N=1 ungrounded configuration.

### 5.4 Idempotency and resume

- Every task writes its completion to `tasks.jsonl` as a single line on success or failure.
- Re-running `geo-analyzer run` on the same day opens the existing `tasks.jsonl`, enumerates completed task keys, and dispatches only the missing ones.
- This makes the tool safe for cron and CI retries.

### 5.5 Grounded vs ungrounded

Both modes are values of a dimension in the matrix. The provider adapter
layer handles the per-provider translation (tool specs, search parameters,
etc.). Results are stored and scored separately; the gap between grounded
and ungrounded scores for the same `(prompt, model)` pair is itself a
reported metric.

### 5.6 Cost visibility

- Every task records `tokens_in`, `tokens_out`, and `cost_usd_estimate`.
- `geo-analyzer run --dry-run` prints the full matrix and estimated total cost without executing.
- If the estimated cost exceeds `config.cost_warning_threshold_usd` (default `$5`), the CLI requires an interactive confirmation (or `--yes` flag for CI).

### 5.7 Sensitivity mode (opt-in)

For one-off investigations where we want to measure generation variance
explicitly (e.g., "given this search-result set, does the model *reliably*
mention Convictional, or is it coin-flip-dependent on sampling?"), the
CLI exposes an opt-in sensitivity mode:

```
geo-analyzer probe "what is the best org health platform?" \
    --model openai:gpt-5:grounded \
    --sensitivity-samples 5 \
    --temperature 0.7
```

This runs N samples at the given temperature and returns the response
distribution — mention rate, SoV variance — so we can see whether a
metric is robust or fragile. Results are not stored as a run; they're
ad-hoc diagnostics.

Sensitivity mode is **never** used in a normal run. It's the
investigator's tool, not the scoreboard's.

## 6. Scoring pipeline

v1 runs **deterministic extraction only** — no LLM judges. Pure code, cheap, reliable, and already covers the top-line metrics. The ensemble-judge design is preserved for v2 in §14.

Framing: get a harness that dumps outputs and extracts clean signals first; iterate on subjective scoring once we've seen the shape of real responses with Claude Code.

### 6.1 Deterministic extraction

All computed in pure Python over the raw response text. No LLM calls. Runs on every sample (so each of the N=3 grounded samples gets independently scored), then aggregated per §5.3.

- **Mention presence (A)** — normalized string match (case-insensitive, word-boundary-aware) against subject name + aliases. Returns bool + character offsets per sample. In grounded mode, both `mention_presence` (majority-vote bool) and `mention_presence_rate` (count of true / N) are emitted.
- **Mention count** — number of distinct mentions per sample. Stored in `tasks.jsonl`; not surfaced as a primary metric.
- **Ordinal rank (B)** — if the response contains an enumerated list (detected via markdown numbering, bullet patterns, or ordinal phrases), parse the list and return the subject's position or `null` per sample. Aggregated as median.
- **Share of voice (C)** — `mentions(subject) / (mentions(subject) + sum(mentions(c) for c in subject.competitors))` per sample, returning `null` when denominator is zero. Aggregated as mean.
- **Brand-legacy conflation (G, dropship confusion)** — fires when `convictional_brand` (any alias) AND any term from the `convictional_legacy_dropship` alias list co-occur in the same sample. Returns bool + both match offsets for audit. In grounded mode, both `brand_legacy_conflation` (majority-vote bool) and `brand_legacy_conflation_rate` (count of true / N) are emitted.
- **Cited URLs (F, recorded but not scored in v1)** — regex-extract URLs per sample; tag any matching Convictional-owned domains. Stored in `tasks.jsonl` for later analysis; not surfaced in the v1 summary.

All extractors write their per-sample outputs plus match offsets to `scores.jsonl`, so the deterministic audit trail is reproducible from the raw response.

## 7. Storage

**v1 is local-only — no remote persistence.** Every run's outputs live under `experiments/geo-analyzer/data/runs/<run-id>/` on the machine that ran it (gitignored). The analyst experience is "open the local CSVs in Claude Code or pandas, optionally paste into a Sheet to share."

This is deliberate. v1's purpose is to answer "does this even work? what does the data look like?" — durability and remote sharing matter less than removing every gate to actually running it. There's no GCP service account to provision, no bucket to create. Clone the monorepo, set provider API keys, run.

v2 layers in the judge ensemble (still local). v3 adds remote persistence (GCS for durability + sharing, BigQuery for SQL/dashboards) — see §14.

### 7.1 Run directory layout

During and after a run, all artifacts live under:

```
experiments/geo-analyzer/
└── data/
    └── runs/                             # gitignored at monorepo level
        └── 2026-04-23-manual/
            ├── manifest.json             # run metadata + catalog snapshot
            ├── tasks.jsonl               # one line per task execution (incl. full response)
            ├── tasks.csv                 # tasks flattened to CSV (no response_text — see below)
            ├── scores.jsonl              # one line per score
            ├── scores.csv                # scores flattened to CSV
            └── summary.md                # human-readable dashboard
```

**Run directory naming** is `YYYY-MM-DD-{trigger}` — `manual` for CLI invocations, `launchd-weekly` / `launchd-monthly` for user-scheduled runs. The trigger suffix avoids collisions between triggers on overlapping days.

`tasks.jsonl` and `scores.jsonl` are written incrementally during the run (append-only). `tasks.csv`, `scores.csv`, and `summary.md` are produced at the end of `geo-analyzer run`, or any time after via `geo-analyzer report`.

**Why CSV alongside JSONL:** Claude Code, pandas, and Google Sheets all eat CSV directly. JSONL retains nested fields that don't flatten cleanly (response text, citation arrays, future judge votes). Both formats coexist so each tool gets the one it likes. `tasks.csv` excludes `response_text` to keep it small (raw responses can be hundreds of KB each); full text remains in `tasks.jsonl` for grep and Claude-Code review.

`goals.yaml` lives at `experiments/geo-analyzer/data/goals.yaml` and **is** committed to git — small, hand-edited, defines targets. Only `data/runs/` is gitignored.

### 7.2 Resume-on-crash

`tasks.jsonl` is append-only. On resume, the runner reads existing lines, builds the set of completed task keys, and dispatches only the missing ones. Local file → no network dependency mid-run.

If you want to retry a fully-failed run from scratch, delete the run directory or pass `--no-resume`.

### 7.3 Sharing findings (without remote storage)

Three options for the v1 era:

- **Paste into a Sheet.** Open `tasks.csv` or `scores.csv`, copy, paste. One-shot snapshot.
- **Upload to Google Drive.** `cp -r` the run directory into your Drive. Slightly ceremonial but durable enough for ad-hoc review.
- **Push to a private gist or attach to a Linear/Slack message.** For a one-off finding.

If sharing becomes routine, that's the signal to land v3 (§14.2 / §14.3).

### 7.4 Credentials

v1 requires only LLM provider API keys. **No GCP service account, no GCS bucket, no BigQuery dataset.** See §11.2.

## 8. CLI

Verb-first. The CLI is the only interface in v1 (no MCP wrapper).

```
geo-analyzer run [--tier L1,L2,L3,L4] [--subject S,S] [--model M,M]
                 [--dry-run] [--resume / --no-resume] [--yes]
geo-analyzer report [RUN_ID] [--since YYYY-MM-DD] [--open-latest]
geo-analyzer status
geo-analyzer catalog validate
geo-analyzer catalog diff
geo-analyzer probe "PROMPT" [--model MODEL_ID]
                  [--sensitivity-samples N --temperature T]
```

- `run` defaults to today's date with `--trigger manual` and resumes any partial run in progress. On clean completion: writes the full run directory locally (`tasks.jsonl`, `scores.jsonl`, `tasks.csv`, `scores.csv`, `summary.md`).
- `report` renders or re-renders the dashboard for a given run from the local `data/runs/<RUN_ID>/` directory. `--open-latest` opens the most recent run's `summary.md` in a browser. `--since` renders a multi-run trend report from local runs.
- `status` prints a one-screen summary of the latest run including goal traffic-lights.
- `catalog validate` runs on every `run` invocation automatically; the standalone command is for pre-commit.
- `catalog diff` shows which prompts/subjects/models changed vs the most recent run, so score-chain impacts are visible before changes land.
- `probe` is a one-off execution that is not stored as a run — intended for ad-hoc exploration and sensitivity investigations (§5.7). Agents can call this directly to do a quick one-off check without writing run artifacts.

### 8.1 Exit codes

- `0` — run succeeded, all goals green or no goals tripped
- `1` — catastrophic failure (unrecoverable error, not a per-task failure)
- `2` — run completed but one or more tasks failed
- `3` — run completed but at least one goal is red

Exit codes are reserved for future automation consumers (cron wrapper, CI) — they have no default consumer in v1 but are stable contract.

## 9. Reports

Only the human-readable summary is produced per run, and it lives in the local run directory alongside the JSONL/CSV. Nothing is committed to the repo per run.

### 9.1 `summary.md` — human dashboard

Generated by `geo-analyzer report` from the local `tasks.jsonl` + `scores.jsonl` of a run, written to `experiments/geo-analyzer/data/runs/<run-id>/summary.md`. One page, skimmable. Sections:

1. **Top line** — table of primary metrics per subject. Binary metrics show **both** the prompt-level rate ("X% of prompts where Convictional was conflated as dropship") and the interaction-level rate ("Y% of all grounded interactions across those prompts conflated"). Deltas vs prior run.
2. **Worst prompts** — for each binary metric, the prompts with the highest interaction-level rate. Surfaces specific topics where the model is most likely to misframe the brand.
3. **Funnel shape** — sparkline per subject showing tier progression (L1 → L4).
4. **Goal progress** — traffic-light list against `goals.yaml`.
5. **Grounded vs ungrounded gap** — biggest deltas, with interpretation.
6. **Cost & runtime** — task count, total cost, total wall time.

The two top-line rates answer different questions:

- **Prompt-level rate** = "for what fraction of *prompts* does the typical answer surface conflation?" (binary majority-vote per prompt × model, then averaged across prompts)
- **Interaction-level rate** = "across all model interactions in this run, what fraction conflated?" (per-sample binary, mean across all samples × all prompts × all models)

Both are useful: prompt-level exposes specific problematic topics; interaction-level estimates what a representative user actually experiences.

Each summary includes the local run directory path (`experiments/geo-analyzer/data/runs/<run-id>/`) so the reader can open the per-sample task data and CSVs for further analysis.

### 9.2 Detailed analysis

Not a report file — interactive analysis on the local run directory:

```
cd experiments/geo-analyzer/data/runs/2026-04-23-manual
# open tasks.csv / scores.csv in pandas, Sheets, or Claude Code
# grep tasks.jsonl for raw responses
```

Cross-run trends in v1 are likewise file-based: `geo-analyzer report --since 2026-01-01` walks all runs in the local directory and emits an aggregated summary. SQL across runs and Looker dashboards arrive in v3 (§14.3).

## 10. Goals

`data/goals.yaml` (relative to `experiments/geo-analyzer/`) is the source of truth for targets. Example:

```yaml
- id: brand-sov-l3-2026q3
  subject: convictional_brand
  metric: share_of_voice
  tier: L3
  target: 0.25
  created_at: 2026-04-23
  target_date: 2026-09-01
  notes: "Q3 positioning target"

- id: category-mention-l2-2026q3
  subject: organizational_health_category
  metric: mention_presence
  tier: L2
  target: 0.30
  created_at: 2026-04-23
  target_date: 2026-07-01
  notes: "Category awareness milestone"

- id: legacy-dropship-l4-eoy
  subject: convictional_legacy_dropship
  metric: mention_presence
  tier: L4
  target: 0.05
  direction: below   # anti-signal: measured value must be <= target
  created_at: 2026-04-23
  target_date: 2026-12-01
  notes: "Legacy association must fade"
```

Required fields:

- `id` — stable string identifier; lets us track a goal's progress even if other fields are edited (e.g., target tightened, deadline pushed). Hand-assigned; no auto-generation.
- `created_at` — date the goal was committed. Anchors the linear interpolation that drives the yellow/red traffic-light: at 50% of elapsed time between `created_at` and `target_date`, you should be at 50% of the way to `target` from the value at `created_at`.
- `direction` — `above` (default — measured value must be ≥ target, for grow metrics) or `below` (measured value must be ≤ target, for anti-signals).

`geo-analyzer status` reads `goals.yaml`, joins to the most recent run's scores, and prints green/yellow/red per goal based on the interpolation. If a goal's `created_at` is after the most recent run, the status shows `pending` (not enough data yet).

## 11. Operations

### 11.1 Repository placement

- **Monorepo:** `convictional/decide` (private)
- **Path:** `experiments/geo-analyzer/`
- **Isolation:** own `pyproject.toml` and `uv.lock`, separate from `experiments/pyproject.toml`. No import dependencies on `app/` or other experiments.
- Inherits the monorepo's branch protection, PR review, and CI gating policies.
- Adds one entry to the monorepo-level `.gitignore`: `experiments/geo-analyzer/data/runs/` (per-run scratch lives there, gitignored — see §7.2).

### 11.2 Secrets

- `experiments/geo-analyzer/.env.example` committed; real `.env` gitignored (covered by monorepo `.gitignore`).
- **LLM provider keys (only thing v1 needs):** `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`.
- **No GCP credentials in v1.** v3 (§14.2 / §14.3) introduces remote persistence and the corresponding service account at that point.

### 11.3 Execution model

**v1 is a CLI run manually or scheduled locally via `launchd`.** No GitHub Actions cron, no centralized orchestrator. Keeps the monorepo's CI clean, defers the workflow-design work, and lets the first user iterate quickly.

**Manual invocation:**

```
cd experiments/geo-analyzer
uv sync
uv run geo-analyzer run --yes
```

Run artifacts land in `experiments/geo-analyzer/data/runs/<run-id>/` (gitignored).

**Scheduled (launchd, per-user):**

The repo ships a sample `experiments/geo-analyzer/launchd/convictional.geo-analyzer.plist.example`. To install:

```
cp experiments/geo-analyzer/launchd/convictional.geo-analyzer.plist.example \
   ~/Library/LaunchAgents/com.convictional.geo-analyzer.weekly.plist
# edit paths, then:
launchctl load ~/Library/LaunchAgents/com.convictional.geo-analyzer.weekly.plist
```

Example .plist fires `uv run geo-analyzer run --trigger launchd-weekly --yes` every Monday at 08:00 local time; output captured to `~/Library/Logs/geo-analyzer/`.

**When to revisit cron:** once the tool proves itself and we want runs to fire regardless of which machine is awake, migrate to GitHub Actions cron (or a GCP Cloud Scheduler hitting a small Cloud Run job). That's §14 future work, not v1.

### 11.4 CI (unrelated to run scheduling)

A single workflow at monorepo `.github/workflows/geo-analyzer-pr.yml` triggers on `push` / `pull_request` events with `paths: ['experiments/geo-analyzer/**']`. It runs:

- `uv sync --frozen`
- `ruff check` + `ruff format --check`
- `pyright`
- `pytest` (unit + fixture tests only; nothing that hits a real API)

No secrets used, no real LLM calls. Fast, cheap, always on PRs.

### 11.5 Dev tooling

Matches the monorepo's existing conventions:

- `uv` for package management (per-subproject `pyproject.toml` + `uv.lock`, same as `app/` and `experiments/`)
- `ruff` for lint + format
- `pyright` (strict) for typing
- `pytest` + `pytest-asyncio` for tests
- `pre-commit` running ruff + pyright (scoped to `experiments/geo-analyzer/**`)

### 11.6 Testing strategy

- **Unit** — deterministic scoring functions at 100% coverage (pure functions).
- **Fixture-based** — canned provider responses asserted against the deterministic extractors.
- **Integration (`@pytest.mark.live`, opt-in)** — one small real API call per provider, run manually when adding a provider.
- **No E2E automated tests of real runs** — too expensive and inherently non-deterministic.

## 14. Deferred to v2

Design thinking captured here so we don't have to re-derive it when the time comes. Nothing in this section ships in v1.

### 14.1 Ensemble LLM-as-judge pipeline

Once we've run the deterministic harness for a few weeks and observed the shape of real responses with Claude Code, add an ensemble judge stage to score subjective fields that deterministic extraction can't touch:

- `sentiment`: `positive | neutral | negative`
- `description_accuracy`: `accurate | outdated | incorrect`
- `category_framing`: `defined | acknowledged | absent`
- `legacy_dropship_association`: judge-graded version of metric G (the v1 deterministic co-occurrence covers the common case; judge catches more nuanced framings like "Convictional, the old dropship tool, is now…")

**Design (preserved from earlier revisions):**

- Two judges per scoring call, majority-vote, third-judge tiebreaker. Never self-judge (model can't judge its own provider's output).
- Default judges: `google:gemini-3-pro` + `anthropic:claude-opus-4-7`. Tiebreaker: `openai:gpt-5.1`. Swaps when the subject provider matches a default judge.
- Trigger: run only on tasks where the deterministic mention check says the subject is present OR the prompt tier is ≥L3. Skips judge cost on ~40-60% of tasks.
- Wrap primary response in delimited block in the judge prompt to mitigate prompt injection: `<response>…</response>` with an instruction to score only content within the delimiters.
- Resolution: binary unanimous → `high`; 2-of-3 → `medium`; three-way split on categorical → `contested`, surface for human review.
- Storage: new BQ table `judge_votes(score_id, judge_provider, judge_model, vote_json, created_at)`. `scores.scoring_method` gains a `judge_ensemble` value; `scores.confidence` gains `high|medium|contested`.
- Review workflow: start with `geo-analyzer judge list --contested` printing a table + writing a patch YAML; `geo-analyzer judge apply <patch>` merges human decisions. Only build a TUI if volume justifies (likely unnecessary at ~5-20 contested scores per run).

### 14.2 GCS canonical archive (v3, first persistence layer)

Once v1 (local-only harness) and v2 (judges, still local) are working, the first persistence layer is GCS. This is the v3 entry point — durability and shareability without committing to a schema.

**Design (when v3 lands):**

- New bucket `gs://${GCS_BUCKET}` in `${GCP_PROJECT}`, location `US`.
- New service account `geo-analyzer-writer@${GCP_PROJECT}.iam.gserviceaccount.com` with `roles/storage.objectAdmin` scoped to the bucket. No other access.
- New CLI command `geo-analyzer push [RUN_ID]` uploads the local `data/runs/<run-id>/` directory to `gs://${GCS_BUCKET}/runs/<run-id>/`.
- New CLI command `geo-analyzer fetch RUN_ID` downloads a remote run to a local directory.
- `geo-analyzer run` gains an `--upload` flag (or `auto_upload: true` in config) so the upload step can run automatically at the end of every run.
- Lifecycle rules: none initially. Storage cost is MB/year; revisit if it ever matters.

**Why we waited:** v1's purpose is "does this work?" and v2's is "are the metrics calibrated?" Neither needs durability. Once we're running regularly and finding things worth sharing, GCS layers in cleanly without changing the local data model.

### 14.3 BigQuery analytical store + dbt (v3, on top of GCS)

Once GCS persistence (§14.2) is in place, sync each run into BigQuery so we can run SQL across runs and build Looker Studio dashboards.

**Design:**

- New dataset `geo_analyzer` (prod) / `dev_geo_analyzer` (dev) in `${GCP_PROJECT}`, location `US`. Matches the `data/bigquery-dbt/` convention.
- Tables: `runs`, `tasks`, `scores` (and `judge_votes` if v2 judges have landed — §14.1). Schemas roughly the same as the local JSONL row shape, partitioned by date and clustered on `run_id`.
- New CLI command `geo-analyzer sync [RUN_ID]` reads the GCS run archive and writes to BQ via `MERGE`. Idempotent. Triggered automatically at the end of `run` once enabled, or manually for backfills.
- Service account gains `roles/bigquery.dataEditor` (scoped to the dataset) and `roles/bigquery.jobUser` (project level).
- dbt: do not add models to `data/bigquery-dbt/models/` until there's a clear analyst use case for marts beyond raw queries.

**Why we waited (further):** by the time we add BQ, we'll have weeks of runs in JSONL/CSV form to inform schema decisions and indexing. Designing the BQ schema upfront would just guess at slices we haven't yet validated.

### 14.4 MCP server wrapper

A thin wrapper exposing `geo-analyzer probe`, `geo-analyzer status`, and a read-only BQ query tool (once §14.3 lands) as MCP tools. Useful if we want Claude Desktop / Code to natively call the tool without shelling out. Not hard to add; just not needed in v1 since agents use the CLI directly.

### 14.5 Scheduled automation (GitHub Actions cron)

When the tool proves valuable and we want runs to fire regardless of which machine is awake, migrate from per-user `launchd` to either:

- **GitHub Actions cron** with `schedule:` triggers — matches the monorepo's existing `demo-janitor.yml` pattern.
- **GCP Cloud Scheduler + Cloud Run** — the tool is Python + runs against GCP resources anyway; a Cloud Run job triggered by Cloud Scheduler is arguably more natural than GH Actions for this specific tool.

Add Slack alerting at this point if on-call volume justifies.

### 14.6 Cross-generation cohort curve

The `convictional_legacy_dropship` anti-signal is specifically a
**training-era artifact**: older models were trained while Convictional
was a dropship company; newer models have had more time to absorb the
repositioning. Running prompts against earlier model generations
reveals the decay curve of the legacy association across time.

This is potentially the most differentiated diagnostic for the
repositioning effort — but it's also a measurement enhancement that
pays off most after we've validated the deterministic harness produces
clean signal at all. v1 establishes that signal; v2 adds the temporal
dimension on top.

**Design (when v2 lands):**

- Re-introduce a `cohort` field on the Model schema (stable string like `"2023-h1"`, `"2024-h2"`, `"2026-h1"`) so cross-provider rollups are possible.
- **Ungrounded mode only.** In grounded mode, answers are driven by the live web search layer — the model's training cutoff barely matters. Including grounded historical runs would mostly add noise and cost.
- One-to-two generations back per provider, focused on OpenAI / Anthropic / Google where prior-generation API access is still available.
- Availability validation at catalog load: probe each historical model on startup; emit a warning (not a failure) for any that return 404/deprecated; pin `active: false` in a follow-up commit.
- Add a new `runs/.../summary.md` section: **cohort curve** — legacy-dropship mention rate and brand-legacy conflation rate ordered oldest → newest, showing whether newer generations "forget" the dropship era.
- ~150 extra API calls per run; older models are cheap so cost impact is small.

### 14.7 Additional providers

Add Perplexity (grounded-only), xAI (once search API stabilizes), and Mistral (ungrounded-only) to broaden coverage. Only after the three-provider v1 has proven the measurement model works and the added cost is worth the additional signal.

### 14.8 Google Trends–driven prompt generation

Augment the hand-authored catalog with prompts derived from actual Google search terms — more likely to reflect how prospects actually search. Weekly Trends query for org-health-adjacent terms, filtered to ones that look like questions, run through a small generator that turns them into L2-L3 prompts.

### 14.9 Content feedback loops

Once we're measuring regularly, the reports themselves become an input to the marketing content pipeline: which topics drag SoV down, which competitors are winning specific L2/L3 prompts, what language the models use to describe us (via sentiment + description accuracy when the judge pipeline lands). Connect the dashboard to content planning, not just monitoring.

### 14.10 Rate-limit-aware concurrency

v1 uses `asyncio.Semaphore` for concurrency caps, which covers in-flight parallelism but not RPM/TPM windows. For ~750 calls/run spread across a few minutes, semaphore is sufficient. When we expand prompt catalogs or run cadence, add a token-bucket / sliding-window rate limiter per provider (ref: bot review comment).
